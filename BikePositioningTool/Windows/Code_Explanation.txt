Here's the full walkthrough of [BikePositionCV.py](BikePositioningTool/Windows/BikePositionCV.py). It's one file (~990 lines) organized into clearly-separated sections. I'll go top-to-bottom, then explain how data flows end-to-end.

## The big picture

It's a **markerless 2D bike-fit tool**. Each video frame goes through one pipeline:

```
camera frame → MediaPipe Pose → 2D joint coordinates → 5 fit angles
   → (while recording) sample one value per pedal stroke
   → aggregate to mean/median/std → save run + report → analyze across runs
```

Everything else (voice, GUI hooks, dashboard) is plumbing around that core.

## 1. Setup constants — what we measure

[BikePositionCV.py:112](BikePositioningTool/Windows/BikePositionCV.py:112) — `L` and `R` map body-part names to **MediaPipe Pose landmark indices** (MediaPipe outputs 33 numbered points; e.g. right knee = 26). You pick `--side` and the code uses that side's six joints (shoulder, elbow, wrist, hip, knee, ankle).

[BikePositionCV.py:117](BikePositioningTool/Windows/BikePositionCV.py:117) — `METRICS` is the single source of truth for the five angles. Each entry is `(key, label, lo, hi, what_it_tunes)`, e.g. `("knee_ext", "Knee Extension", 32, 38, "Saddle height")`. Almost everything (panel, report, CSV, dashboard) loops over `METRICS`, so changing a target range here updates the whole app.

## 2. The geometry — turning points into angles

This is the mathematical heart, and it's tiny:

- [`angle_3pt(a, b, c)`](BikePositioningTool/Windows/BikePositionCV.py:138) — the interior angle at joint `b`, via the dot-product formula `cos θ = (v1·v2)/(|v1||v2|)`. Used for knee/hip/shoulder/arm.
- [`angle_to_horizontal(a, b)`](BikePositioningTool/Windows/BikePositionCV.py:146) — angle of a line vs horizontal, using `atan2`. Used for back angle (hip→shoulder vs the floor).
- [`px(...)`](BikePositioningTool/Windows/BikePositionCV.py:152) — MediaPipe returns normalized 0–1 coordinates; this scales them to pixels.
- [`compute_angles(p)`](BikePositioningTool/Windows/BikePositionCV.py:157) — the key function. Given a getter `p("knee")`, it returns all five angles in a dict. Note `knee_ext = 180 − interior_knee_angle` (how *bent* the knee is at the bottom), and it stashes `_knee_interior` for internal use.
- [`metric_stats(values)`](BikePositioningTool/Windows/BikePositionCV.py:172) — takes a list of per-stroke samples and returns `{n, mean, median, std, min, max, cv}`. This is what makes the output "scientific."

## 6. Voice control (offline)

- [`class Speaker`](BikePositioningTool/Windows/BikePositionCV.py:424) — text-to-speech on a **background thread** (a queue + worker, so speaking never freezes the video). It prefers **Piper** (natural neural voice), falls back to Windows SAPI (`pyttsx3`), then silent.
- [`resolve_piper_model`](BikePositioningTool/Windows/BikePositionCV.py:495) / [`resolve_vosk_model`](BikePositioningTool/Windows/BikePositionCV.py:514) — locate the offline models, **auto-downloading** them on first use.
- [`start_voice_listener(cmd_queue, ...)`](BikePositioningTool/Windows/BikePositionCV.py:537) — spawns a thread running **Vosk** on the mic with a *restricted grammar* (only your command words). When it hears "start"/"stop", it pushes `"start"`/`"stop"` onto `cmd_queue`, which the main loop drains. Threads + a queue is the clean way to bridge async audio into the frame loop.

## 8. `main()` — orchestration + the live loop

[`main()`](BikePositioningTool/Windows/BikePositionCV.py:819) does:

**a. Args & early exits** — parses all the flags; `--list-mics` and `--analyze` handle their job and `return` immediately (no camera needed).

**b. Setup** — resolves the camera source, creates the timestamped run folder, sets up the Speaker + Vosk listener if `--voice`.

**c. Two nested helpers** — [`begin_recording()`](BikePositioningTool/Windows/BikePositionCV.py:934) and [`end_recording()`](BikePositioningTool/Windows/BikePositionCV.py:960). These hold the recording state (using `nonlocal`), open/close the `VideoWriter`, reset the per-stroke buffers, and speak the confirmation. Both SPACE and voice route through the *same* two functions, so behavior is identical.

**d. The frame loop** (the engine) — each iteration:
1. Read a frame, run `pose.process()`.
2. `compute_angles()` for the live values.
3. **Pedal-stroke detection** (while recording): it watches the ankle's vertical position. The bottom of a stroke = ankle at its lowest (max pixel-y). It tracks the running max (`peak_y`), and once the foot rises back up by ~4% of frame height (hysteresis to avoid double-counting), it records that bottom frame's angles as **one stroke sample**, then recomputes the running median.
4. Draw skeleton + angle labels; save a representative bottom-of-stroke frame for the `.jpg`.
5. Compose video + panel, `imshow`, and write to the video file if recording.
6. Drain `cmd_queue` (voice commands) and handle keys (SPACE/R/Q).

**e. On quit** — aggregates the per-stroke samples via `metric_stats`, picks the **median** as each headline value (or falls back to the single deepest frame if you stopped before a full stroke), saves the snapshot/report, prompts for name+note, writes `run.json`, and renames the folder.

## Why it's structured this way

- **`METRICS`-driven** — add or retune an angle in one place.
- **Pure functions for math/IO, threads for async** (voice/TTS) so the frame loop stays simple and never stalls.
- **Subprocess-friendly** — the GUI launches this same script with flags, and `--analyze` is a self-contained mode, so the GUI never has to import the heavy CV stack.
